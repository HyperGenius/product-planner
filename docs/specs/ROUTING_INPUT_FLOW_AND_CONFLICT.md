# 工程情報の段階的入力フローと設備衝突への対応方針

## 背景

工程情報はベテラン社員の頭の中にしかない暗黙知であり、初期登録時点で完全な状態を求めることは現実的ではない。そのため「不十分な状態のまま運用を始め、注文処理の過程で徐々に完成させる」という前提でフローを設計する。

ProductPlannerが提供する価値は「現場の調整を消すこと」ではなく「調整が必要なタイミングを早く見つけられること」である。この方針を本Issueにおける全ての設計判断の前提とする。

## 基本フロー

```
製品名のみ入力
  → 転送メールから注文内容を抽出して下書き作成
  → 工程が不十分な場合にベテラン社員が入力して再シミュレーション
  → 納期とガントチャートへ登録
```

## 決定事項

### 1. 工程確定フラグによる判定

- 工程レコードが存在しない製品は無条件で「不十分」と判定する。
- それ以外は工程レコード単位の「確定フラグ」で判定する。未確定の工程を含む下書きは、確認を促す通知を出す。
- 通知頻度は「下書きを開いたセッション内で一度だけ表示」「前回確認から一定件数・一定日数経過後に再提示」など、頻度制御を入れて過剰な催促を避ける。
- 確定フラグは恒久的なものではなく、紐づく設備マスタの変更時に自動的に無効化されるべき、という前提を設計上残しておく(初期実装では見送り可)。

### 2. マスタへの書き戻しと品質管理

- ベテランが入力した工程情報は品番マスタへ書き戻す。
- 確定フラグを立てられるロールを制限することで、入力内容の暫定品質を担保する。
- 暫定品質チェックの有効/無効はテナントごとの設定とし、運用の煩雑さを回避する(例: パイロット顧客のように入力者が一人の場合は無効化)。
- チェックを無効化している場合でも、入力者のロールとタイムスタンプはレコードに保持する。将来複数人運用に切り替わった際に、過去データの信頼度を判断する材料として必要になるため。

### 3. ベテラン確認のキュー方式

- リアルタイム割り込みではなく、未確定工程を含む注文をキューに積み、ベテランが手の空いたタイミングで定期的に処理する方式を採用する。
- キューの並び順は受注日順ではなく、顧客希望納期からの逆算で残バッファが少ない注文を優先表示する。
- 見せ方として、未確定件数や最も切迫した注文のバッファをダッシュボードまたは日次ダイジェストで可視化する案を検討する。

### 4. 下書き放置時のフォールバック

- 工程が未確定のまま放置された注文は、ガントチャートへの登録を行わず、顧客希望納期のみを表示する。
- フォールバック条件は「注文の下書き状態」ではなく「工程未確定」を主軸とする。注文自体は登録済みだが工程が未確定、というケースが通常に発生するため、一貫性を保つ。

### 5. 設備衝突への対応方針

工程情報が曖昧なまま運用される以上、設備の取り合い(スケジュール衝突)は避けられない前提とする。現場の擦り合わせをシステム上で再現することは目指さず、衝突の検知と可視化に投資する。

- 確定済みの工程は設備を排他的に確保する「確定済みスロット」として扱う。
- 未確定の工程から生じる仮配置は排他制御をかけず、重複を許容する。重複表示自体を「ベテランが確認すべき案件」のシグナルとして扱い、3.のキューの仕組みを再利用する。
- 衝突時の優先順位は確定フラグの有無を基準とする(確定済みが優先、未確定側が調整対象)。両方が確定済みで衝突するケースは、システムで解決を試みず人間に判断を委ねる。
- 汎用設備と専用設備で扱いを分ける案を検討する。専用設備は稼働率100%を前提とせず、意図的にバッファを残す設定をマスタに持たせることで、現場の「詰めすぎない」判断に近づける(初期実装では見送り可、将来のテナント設定として追加)。

## Non-Goals(本Issueの対象外)

- 設備衝突を自動で解消するアルゴリズムの実装
- 現場の調整プロセスそのものの完全な代替
