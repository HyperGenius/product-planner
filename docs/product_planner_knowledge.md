# ProductPlanner ナレッジドキュメント

> 作成日: 2026-06-10  
> 目的: ドメイン知識・設計思想・開発方針の整理

---

## 1. プロジェクト概要

### 顧客・背景
- 中小製造業（工場）の社長からの依頼
- 既存システム: テクノア Techs（生産管理）+ 勘定奉行（経理）
- Techsのデータは全件ダンプ済み（全工程・全製品）、ただしデータ品質はイマイチ
  - 希望納期の割り込み未反映
  - 数量変更の未反映
  - →Techsが信頼されていないため入力されなかった負のループが原因

### 社長の意向
- **最重要課題: 顧客への納期回答**
- 生産管理の現状: ホワイトボード＋ベテラン社員の経験による属人的運用
- 毎日の朝・昼ミーティングで優先順位を人間が判断
- デジタル化＋属人化排除が目標
- ベテラン社員は経験で現場を回しており、業務プロセスの言語化スキルは高くない

## 2. ドメインモデル（現状把握）

### 受注データの構造（最小項目）
```
- 製品
- 顧客
- 数量
- 希望納期
```

### スケジューリングロジック（現状）
- 製品1つを製造するために必要な各工程の時間が登録済み
- 数量 × 工程時間 = 必要時間を算出
- 工場稼働時間で工程を配分
- **最大の制約: 設備の奪い合い**（複数製品が同一設備を使用）
- 設備利用時間はテーブルに保存済み

### 優先順位決定（現状）
- 入力順をベースに、割り込みはマニュアル操作
- 朝・昼ミーティングで人間が優先順位を決定
- →**このミーティングの意思決定支援がProductPlannerの本質**

## 3. 現在の実装

### 技術スタック
- Frontend: Next.js / Vercel
- Backend: FastAPI / Cloud Run
- DB: Neon（サーバーレスPostgres）
- Auth: Clerk
- IaC: Terraform + GitHub Actions

### 現状の機能
- ざっくりのガントチャート出力（納期回答にフォーカス）
- 受注データとガントチャートは**現状手動でリンク**（未連携）

### 既知の課題
- 受注入力とガントチャートが未連携
- 受注入力の手間がベテランの負担になっている
- データ品質の担保が運用依存

## 4. 受注入力フローの設計方針

### 入力経路（3経路）

| 経路 | 方法 | 実装方針 |
|------|------|----------|
| メール注文 | Gmail API + Claude API で自動抽出 | PoC優先 |
| Fax・電話注文 | 複合機横の8インチタブレットから手入力 | 入力項目を最小化 |
| 既存データ | Techsダンプ済み | 移行済み |

### メール連携の設計思想
- 注文メールはフリーフォーマット想定
- Claude APIで「製品・顧客・数量・希望納期」を抽出
- **全自動ではなく確認画面を挟む設計**
  - 誤抽出のリスクヘッジ
  - ベテランの信頼を得るための一手間
- フロー: メール受信 → Claude API抽出 → 確認画面 → 承認 → 受注登録 → ガント反映

### PoCの進め方
- 本番はOutlookドメインだが、PoC期間は社長に許可をもらい自分のGmailに転送
- Gmail API + Claude API で実装
- 本番移行時にMicrosoft Graph API対応を検討

## 6. ドメイン知識の収集方針

### 基本方針
**「使ってもらう → 意見をもらう → 改善する」のサイクルを回しながらドメインモデルを整理する**

- ベテランの暗黙知はインタビューより「これじゃない」という反応から逆算する
- 完全な仕様定義を待たずに動くものを見せる

### リスク
- ベテランごとにプロセスが微妙に異なる可能性
  - スキーマ変更が必要になるタイミングに注意
  - 特に工程マスタ・優先度フラグ周辺

## 7. 顧客との関係性・進め方

### 訪問・コミュニケーション計画
- 月1回の現地訪問（節目のデモ＋方向確認）
- 隔週1回のチャット（小さな確認＋進捗報告）
- Vercelプレビューデプロイで随時URLを送付

### 初回デモで見せるもの
1. 現状アプリ（ガントチャート）
2. メール連携PoC（Gmailデモ）
   - 「注文メールがガントに反映される」を目の前で見せる

### ビジネスモデル
- 費用: 個人開発の範囲内（自己負担）
- 目標: 月額1万円のSaaS
- 横展開: 同規模の中小製造業への展開

### 注意点
- 社長は「やらねばならない、でも時間がない」状態
- **社長の手を煩わせない設計が最重要**
- フィードバックを求めすぎると疎遠になるリスク

## 8. 設計上の判断記録

| 判断 | 理由 |
|------|------|
| 優先順位は入力順＋手動割り込み | 現場の判断にはデータ化されていない変数が多すぎる。自動化は信頼を得てから |
| 確認画面を挟むメール連携 | 誤抽出による信頼喪失を防ぐ。全自動は段階的に |
| PoCはGmail転送で進める | Microsoft Graph APIの認証周りはPoCの本質ではない |
| 朝昼ミーティング支援を中期目標に | まず動くものへの信頼を得てから同席・観察する |
