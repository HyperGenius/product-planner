# UI文言ガイドライン

ProductPlanner の画面に表示するテキスト(見出し・ボタン・説明文・バッジ・バナー・メッセージ)を書くときのルール。
人間の開発者と Claude Code の両方が対象。UIを追加・変更するときは、このガイドラインに沿って文言を書く。

## 1. 基本原則

1. **画面は利用者の「次の行動」のためにある。** 仕組みの説明は画面に書かない。
2. **説明文を足す前に、UIで表現できないかを考える。** できない操作はボタンを置かない。順番は並び順で示す。状態の変化は起きたときに知らせる。
3. **長い説明文が必要に見えたら、UIに機能が足りていない。** 文章で回避手順を教える前に、その手順を操作として用意できないかを検討する。
4. **同じことは1回だけ書く。**

## 2. テキストの種類と置き場所

画面に出すテキストは、下の7種類のどれかに当たる。置いてよいのは上の3種類だけ。

| 種類 | 例 | 扱い |
|---|---|---|
| 行動 | 「送品済みにする」「名寄せする」 | 画面に置く。ボタン・見出しに使う |
| 判断材料 | 一部送品、納期超過、日報の漏れ | 画面に置く。判断が変わる**例外だけ**を出す |
| データの鮮度 | 取り込み日時、何日分までか | 1行に詰める。古いときだけ警告として目立たせる |
| 仕組みの説明 | 「名寄せすると明細が受注と結び付き、件数が変わります」 | 画面に書かない → ヘルプへ |
| 原則・ガードレール | 「ここでは送品済みにしません」 | 画面に書かない → ボタンを置かないことで表現する |
| 状態の移り変わり | 「取り込まれると①へ移ります」 | 画面に書かない → 起きたときにトーストで知らせる |
| 抽出条件 | 「直近60日。得意先ごとにまとめています」 | 画面に書かない → 必要ならフィルタUIとして見せる |

## 3. 迷ったときの3つの問い

1. **このテキストを消したら、利用者は操作を間違えるか。** 間違えないなら、消すかヘルプに移す。
2. **このテキストは誰の不安を解消しているか。** 開発者の不安なら消す。
3. **ラベルの補足に1文が必要か。** 必要なら、補足ではなくラベルのほうを直す。

## 4. 書き方のルール

### 4.1 ボタン・見出し
- ボタンは「〜する」という動詞で書く:「送品済みにする」「受注を起票する」
- 一覧やセクションの見出しは、そこでやる行動か、対象の名前にする
- 「〜について」「〜の管理」「〜一覧」のような中身のない見出しは避ける

### 4.2 説明文
- 説明文は**1画面に1か所まで、1行まで**(全角40字が目安)
- 副題でページの仕組みや並び順を説明しない。説明が必要なら副題ごと消す
- 書くのは、利用者が操作を間違えそうな箇所の**直前**だけ

### 4.3 件数と単位
- 件数には必ず単位を付ける:「3注文」「2商品」「1明細」
- 単位の違うものを足し合わせない
- ハブなどに出す件数は、遷移先の一覧の行数と一致させる

### 4.4 バッジ・タグ
- 全行に共通するタグは出さない(その一覧に入っている理由そのものになっているため)
- 出すのは、行ごとに判断が変わる例外だけ
- 色の意味はアプリ全体で揃える(赤 = 期限超過・要対応、橙 = 期限が近い、など)

### 4.5 バナー・警告
- 形は「**何が起きているか(1文)+ ボタン**」にする
- 対処したら何が変わるか(因果)は書かない。対処した後にトーストで結果を見せる
- 例:「弥生の得意先1件・商品2件がアプリに未登録です」[名寄せする]

### 4.6 トースト・完了メッセージ
- 状態の移り変わりは、起きたときにここで伝える
- 例:「名寄せで3明細が結び付き、2注文を送品済みにできるようになりました」

### 4.7 データの鮮度
- 1行に、ソースごとに「どこまでのデータか」だけを書く:「弥生 11/21売上分まで・日報 11/25 9:15」
- 普段は控えめに表示し、更新が止まっているときだけ警告として目立たせる

### 4.8 データ不整合の表示
- 照合エラーやマスタの不一致といった内部の状態を、行の中に文章で書かない
- 行には「要確認」の印だけを出し、詳細は行を開いたとき(詳細パネルなど)に出す

## 5. 用語

画面には、利用者の業務の言葉を使う。実装やロジックの言葉は使わない。

| 使わない(内部語) | 使う(画面語) | 備考 |
|---|---|---|
| 当たる/当てる | (文を組み直す) | 例:「受注に当たらない明細」→「受注が無い明細」 |
| 照合/未照合 | 未登録/結び付いていない | |
| 候補 | (行動名で置き換える) | 例:「送品の候補」→「送品済みにする」 |
| 追いついていない | 未入力/漏れ | 何に対して遅れているのかを書く |
| 起票漏れ | 受注が無い | 括弧で併記しない |
| 自動では〜しません | (書かない) | |
| 割り付け/未割当 | 結び付く/結び付いていない | 例:「受注に割り付けられなかった実績」→「受注に結び付かなかった実績」 |
| 類似度 | (出さない) | 似ている順に並べ、品名・品番を見比べて選ばせる |
| キュー | (一覧の見出し・ページ名で置き換える) | 例:「未照合キューに戻す」→「対象外から戻す」 |

用語集は初版。新しく内部語に気づいたら、ここに追加する。
「名寄せ」は利用者がすでに業務で使っている言葉かどうかを確認してから扱いを決める(未決)。

## 6. 禁止パターン

- [ ] 「〜しません」という否定形でシステムの振る舞いを説明している
- [ ] 抽出条件(期間・集計単位・表記のルール)を説明文に書いている
- [ ] 同じ説明が2か所以上にある(カードと一覧見出し、情報ボックスとバナーなど)
- [ ] 副題がページの仕組みや並び順を説明している
- [ ] 「〜すると〜が〜して〜が変わります」という因果の連鎖を書いている
- [ ] 利用者にデータの入力の仕方を変えさせて、ロジックに合わせてもらう手順を書いている
- [ ] 全行に同じバッジが付いている
- [ ] 単位のない件数、または単位の違う件数の合算がある

## 7. ヘルプ

- 仕組みの説明は、ページごとのヘルプ(見出しの横の「?」から開く)に書く
- ヘルプに書いてよいのは、判定条件、データの出どころ、状態の移り変わり、設計上の原則
- 画面に書きたくなった説明は、まずヘルプに書く。ヘルプという置き場所がないと、説明文は画面に戻ってくる

## 8. 修正前後の例:送品の消し込み画面

| 箇所 | 修正前 | 修正後 |
|---|---|---|
| 副題 | 弥生の売上明細と日報の進捗から、送品の消し込みでやることを片付ける順に並べています | (削除) |
| 鮮度の行 | 弥生の売上伝票: 11/22 09:30 に取り込み / 取り込み状況 弥生の売上明細: 11/21 売上分まで 日報の進捗: 11/25 09:15 時点 弥生の名寄せ | 弥生 11/21売上分まで・日報 11/25 9:15 |
| バナー1 | 弥生の得意先1件・商品2件が、アプリの顧客・製品と結び付いていません。名寄せを済ませると、その明細が受注と結び付き、①送品済みにする・③受注を起票するの件数が変わります | 弥生の得意先1件・商品2件がアプリに未登録です [名寄せする] |
| バナー2 | 送品先の受注が1件に決まらない弥生の商品が1件あります。受注の顧客注文番号・希望納期を弥生の備考に合わせると… | 送り先の受注を決められない明細が1件あります [受注を選ぶ](受注を選ぶ操作をUIとして用意する) |
| 情報ボックス | 送品の記録は弥生が正です。①は弥生で送品を確かめられた注文なので… | (削除。②にボタンがないことで伝わる) |
| カード① | 弥生で受注数量の送品を確かめられた注文です。内容を見て送品済みにします | 弥生で出荷済み。確認して送品済みにする |
| カード② | 弥生ではまだ受注数量の送品を確かめられていない注文のうち、最終工程が完了した・納期を過ぎた・納期が近いものです。弥生で出荷を確かめます | 弥生に未計上。出荷したか確かめる |
| 一覧見出しの補足 | 弥生で受注数量の送品を確かめられた注文です。内容を見て「送品済みにする」を押してください(自動では送品済みにしません) | (削除) |
| ①の理由列 | 全行に「弥生で送品済み」 | 例外だけを出す(一部送品、日報の漏れなど) |
| ③の補足 | 対象: 弥生の売上日 9/23〜11/21(取り込んだ明細の直近60日)。得意先・商品コードごとにまとめています。弥生の表記は最新の明細の値です | (削除。必要なら期間フィルタにする) |
| 参考のラベル | 弥生の送品数に日報の実績が届いていない注文 | 日報が未入力の出荷済み注文 |

## 9. レビューのチェックリスト(PR用)

- [ ] 追加・変更したテキストを、2章の7種類のどれかに分類できる
- [ ] 画面に残したテキストは「行動・判断材料・データの鮮度」のどれかに当たる
- [ ] 6章の禁止パターンに当たるものがない
- [ ] 5章の用語集の内部語を使っていない
- [ ] 説明文は1画面に1か所、1行以内に収まっている
